Architecture Design
AWS High Availability Multi-AZ Well-Architected Terraform Fundamentals

Highly Available WordPress on AWS

Business problem: A content platform running on a single server loses availability during traffic spikes or infrastructure failures. The goal was to design a fault-tolerant, scalable architecture that eliminates single points of failure.

Key architecture decisions:
  • Multi-AZ VPC with public and private subnets for network isolation
  • Application Load Balancer for traffic distribution and health checking
  • EC2 Auto Scaling to handle traffic changes without manual intervention
  • RDS Multi-AZ for database redundancy and automated failover
  • Amazon EFS for shared WordPress file storage across instances
  • CloudFront and S3 for static asset delivery and origin offloading
  • IAM roles and SSM Session Manager to avoid bastion host exposure
  • CloudWatch alarms for availability and error rate monitoring

My role: Designed the architecture, created the architecture diagram, documented service selection rationale using the Well-Architected Framework, and practiced foundational Terraform provisioning for selected components.

AWS Serverless Lambda API Gateway DynamoDB

Serverless Three-Tier Application

Business problem: Many workloads do not need always-on servers but still require a scalable, reliable backend. The goal was to design a serverless architecture that scales automatically and reduces operational overhead.

Key architecture decisions:
  • API Gateway as the managed front door for HTTP requests
  • AWS Lambda for business logic — no servers to manage or patch
  • Amazon DynamoDB as a fully managed, serverless NoSQL data layer
  • IAM roles scoped to least-privilege for each Lambda function
  • CloudWatch for logging and basic operational monitoring

My role: Designed the application tier architecture, documented the service selection rationale, created an architecture diagram, and built a proof-of-concept demonstrating the Lambda and API Gateway integration.
