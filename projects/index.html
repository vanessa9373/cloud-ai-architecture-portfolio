AWS High Availability Multi-AZ Well-Architected Terraform Fundamentals

Highly Available WordPress on AWS

Business Problem

A content platform running on a single server loses availability during traffic spikes or infrastructure failures. The goal was to design a fault-tolerant, scalable architecture that eliminates single points of failure and keeps the platform accessible during common AWS infrastructure events.

Requirements & Constraints

  • High availability across multiple Availability Zones
  • Automatic scaling in response to traffic changes
  • Secure access to EC2 instances without exposing bastion hosts
  • Shared file storage accessible by all application instances
  • Cost-conscious design using managed services where appropriate

Architecture & Service Selection

  • Multi-AZ VPC with public and private subnets — network isolation keeps database and application layers off the public internet
  • Application Load Balancer — distributes traffic across healthy EC2 instances and performs health checks
  • EC2 Auto Scaling Group — automatically adjusts capacity based on demand, without manual intervention
  • RDS Multi-AZ (MySQL) — automatic failover to a standby replica if the primary database fails
  • Amazon EFS — shared WordPress files (plugins, uploads, themes) accessible across all EC2 instances
  • CloudFront + S3 — CDN delivery of static assets reduces origin load and improves global response times
  • IAM roles + SSM Session Manager — least-privilege access without bastion host exposure
  • CloudWatch alarms — monitoring for availability and error rate signals

Security Considerations

  • EC2 instances placed in private subnets — no direct internet exposure
  • IAM roles scoped to least privilege for each component
  • SSM Session Manager used for secure shell access without opening port 22
  • S3 bucket access restricted via bucket policy and CloudFront origin access control

Trade-offs Considered

  • EFS adds shared storage cost but is necessary for WordPress file consistency across multiple instances
  • Multi-AZ RDS increases database cost but is essential for automatic failover without manual intervention
  • CloudFront adds complexity but reduces origin traffic and improves performance for geographically distributed users

My Role & What I Learned

I designed the architecture, created the architecture diagram, documented service selection rationale aligned with the Well-Architected Framework, and practiced foundational Terraform provisioning for selected components. This project deepened my understanding of how the Reliability and Security pillars translate into specific AWS service decisions.

AWS Serverless Lambda API Gateway DynamoDB

Serverless Three-Tier Application

Business Problem

Many workloads do not require always-on servers but still need a reliable, scalable backend. Managing and patching servers adds operational overhead that can be eliminated with a serverless approach. The goal was to design an event-driven backend that scales automatically and reduces the operational burden on a small team.

Requirements & Constraints

  • No server management — fully managed compute layer
  • Scales to zero when not in use to minimize cost
  • Secure API access with proper identity controls
  • Reliable data persistence without managing database infrastructure

Architecture & Service Selection

  • API Gateway — managed HTTP front door; handles routing, throttling, and authorization
  • AWS Lambda — stateless business logic execution; scales automatically with no server management
  • Amazon DynamoDB — fully managed NoSQL data layer; serverless scaling with no database administration
  • IAM roles — least-privilege execution roles scoped to each Lambda function
  • Amazon CloudWatch — log capture and basic operational monitoring for Lambda functions

Security Considerations

  • Lambda execution roles scoped to minimum required DynamoDB actions
  • API Gateway configured with appropriate authorization for protected endpoints
  • No server access to manage reduces attack surface compared to EC2-based alternatives

Trade-offs Considered

  • Lambda cold starts can add latency for infrequently invoked functions — acceptable for this use case
  • DynamoDB requires careful schema design upfront; changes are more complex than relational models
  • Serverless is cost-effective at low to moderate usage but may be less cost-efficient at very high sustained throughput compared to reserved EC2

My Role & What I Learned

I designed the application tier architecture, documented the service selection rationale, created an architecture diagram, and built a proof of concept demonstrating the Lambda and API Gateway integration. This project developed my ability to explain serverless trade-offs in business terms and gave me hands-on Lambda and DynamoDB experience.

AWS Elastic Beanstalk Virtual Experience Solution Design Forage

AWS APAC Solutions Architecture — Forage Virtual Experience

Context

This is a structured virtual work simulation through Forage that mirrors an entry-level Solutions Architect engagement. It is not professional employment — it is a real architecture exercise in a simulated customer context, completed to develop and demonstrate SA communication skills.

Customer Scenario

A growing company needed guidance on improving their application's performance and scalability as their user base expanded. The challenge was to recommend an architecture that would allow them to scale without increasing operational complexity.

What I Completed

  • Reviewed the customer scenario and identified the core scalability requirements
  • Recommended an Elastic Beanstalk architecture to provide managed deployment, auto-scaling, and health monitoring without requiring the customer to manage underlying infrastructure
  • Created an architecture diagram illustrating the proposed solution
  • Considered scalability and cost trade-offs in the recommendation
  • Communicated the recommendation in business-focused language appropriate for a non-technical stakeholder

What I Learned

This exercise developed my ability to move from a customer requirement to an architecture recommendation, document the decision rationale, and communicate a technical solution in clear language. It reinforced the importance of matching service selection to a customer's operational maturity rather than choosing the most technically complex option.
